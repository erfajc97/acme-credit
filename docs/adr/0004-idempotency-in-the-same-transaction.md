# 0004 — Idempotency keys stored in the same transaction as the effect

- **Status:** accepted
- **Date:** 2026-10-21
- **Requirements:** R-08d, R-08c
- **Rules:** MO2, MO4

## Context

Money requests get retried: the network simulator retries on timeouts, a browser double-submits,
and a proxy replays. A retry must return the original result and never repeat the effect. The
same key sent with a different payload is a client bug and must be refused.

## Options considered

### A. Cache (Redis) of recent keys

- **Pros:** fast.
- **Cons:**
  - The key and the effect commit separately. A crash in between either repeats the effect or
    loses the answer.
  - It adds a Redis we do not otherwise need.

### B. `idempotency_keys` table written inside the money transaction ✅

- **Pros:** the key, a request hash (SHA-256 of the canonical body plus the route), the response
  status and body all commit atomically with the effect.

## Decision

**B.**

- **Key:** `Idempotency-Key` is REQUIRED (a UUID) on every POST that moves money. It is
  generated by the client and survives reloads: session storage in the web app, the request id
  in card-network.
- **Scope:** the key is unique per `(scope, key)`; the scope is the caller (customer id, or
  `network`).
- **Flow:**
  1. Insert a `pending` row in its own short transaction, or find the existing row.
  2. Run the effect, then save the response in the effect's transaction.
- **Duplicates:**
  - same key + same hash, completed → replay the stored response;
  - same key + same hash, still pending → 409 `idempotency.in_progress`;
  - different hash → 409 `idempotency.key_reused`.
- **Retention:** keys are kept 30 days.

## Consequences

- DTOs, client types and service signatures declare the key as required (MO2 check).
- Tests:
  - a replay gives one effect and the identical response;
  - the same key with another body → 409;
  - two concurrent first requests with one key → one effect.

## Implementation

F2 (`core/idempotency`); every money route uses it from F3 on.

## Amendment (2026-10-22, H2): a lease on the claim

A request that died after claiming its key (process killed, deploy, OOM) left the row
`PENDING` forever: every retry answered 409 `idempotency.in_progress` and the action could
never be done with that key. Each claim now carries a lease (`locked_until`, 60 s, longer than
any attempt can run) and an `attempt` number:

- same key + same hash, `PENDING` and the lease still live → 409 `idempotency.in_progress`;
- same key + same hash, `PENDING` and the lease lapsed → the retry takes the key over with ONE
  conditional update (`attempt` + 1, new lease); of N racing retries exactly one wins;
- every write of the record (resource, response, stored error, release) is conditional on the
  attempt that owns it, and the response is written in the effect's transaction: a slow first
  attempt that finishes after a takeover fails that write and its effect rolls back, so the
  effect commits at most once per key (MO2).

Tests: `idempotency.spec.ts` (boundary of the lease, takeover, stale owner rolled back),
`domain-hardening.int-spec.ts` (crashed claim + lapsed lease → one effect; live lease → 409;
five racing retries → one effect).
